# thinkppt - 技术方案

## Context

产品定位：**先想清楚，再一键成稿的 AI PPT 工具**，面向职场汇报和学术答辩（详见 `docs/产品策划.md`）。产品按**理解 → 重构 → 呈现**三阶段推进：理解阶段看清汇报要讲什么，重构阶段用 5W2H / AB+SCQA+SAP / 金字塔 MECE 把内容重组成站得住的结构，呈现阶段把结构逐层确认展开、一键成稿成 PPT，结构持久保存、随时可续接。

现有代码实现的是这条主线的**早期版本**（"drafting → expanding"两阶段：拟定大纲 → 锁定式逐步展开子步骤），这套状态机和交互模式本身是要保留和复用的核心资产，不需要推倒重来；需要新增和修复的是：结构化的"理解/重构"阶段、持久化、导出（已具备 PPT 导出雏形，需完善），以及几个现存的代码问题。

本文档面向下一轮实现，本轮只做规划，不改动 `electron/`、`src/` 下的任何源码。

## 现状代码基线与已知问题

当前代码已经跑通的核心逻辑：

- **数据流**：`App.tsx`（持有 `usePlanGenerator` hook）→ `PlanView.tsx` → `StageCard.tsx`，AI 调用经 `preload.ts` → IPC → `electron/ipc/ai-handler.ts` → `src/lib/ai/{openai,anthropic,deepseek}.ts` provider → `prompts.ts` 模板 → `parseJSONArray` 解析。
- **两阶段状态机**（`Plan.mode`: `'drafting' → 'expanding'`）：drafting 阶段生成 3-5 个阶段标题、支持整体/单阶段反馈重写；确认后进入 expanding 阶段，除第一阶段外全部锁定，逐个阶段展开子步骤、反馈修改、确认后解锁下一阶段。这套"锁定式渐进展开"机制是产品目前唯一验证站得住脚的差异化，新方向要**原样保留并复用**，作为"呈现"阶段的执行引擎。

已核实的 4 个代码问题（下一轮实现时需要一并处理）：

1. **类型缺字段**：`src/components/StageCard.tsx`、`src/hooks/usePlanGenerator.ts` 大量读写 `stage.confirmed`、`stage.locked`，但 `src/types/index.ts`（即 `@shared/index`）里的 `PlanStage` 接口没有声明这两个字段，类型和实际用法脱节。
2. **"已确认阶段上下文"链路断裂**：`usePlanGenerator.ts` 计算了 `confirmedStages` 并传给 `window.api.expandStage`/`refineSubSteps`，但 `electron/ipc/ai-handler.ts` 的 `expand-stage` handler 直接丢弃这个参数（硬编码传 `[]`）；`refine-sub-steps` 虽转发了参数，但 `AIProvider` 接口（`src/lib/ai/types.ts`）、`openai.ts`/`anthropic.ts` 实现、以及 `prompts.ts` 里的 `buildExpandStagePrompt`/`buildRefineSubStepsPrompt` 都不接收也不使用它。AI 目前完全无法感知已确认阶段的内容。
3. **无持久化**：`electron/store.ts` 只用 `electron-store` 保存 `AppSettings`（API Key），不保存 `Plan`。关闭或刷新应用，当前计划和所有进度全部丢失。
4. **无全局呼出**：`electron/main.ts` 只创建一个普通 `BrowserWindow`，没有注册全局快捷键或托盘图标。

## 目标架构（下一轮实现方向）

### 数据模型演进方向

现有模型：`Plan { mode: 'drafting'|'expanding', stages: PlanStage[] }`，`PlanStage { title, description, subSteps }`。

新方向需要模型能表达三个阶段各自的产出，而不只是"一份阶段列表"：

- **理解阶段产出**：这件事的结构——构成要素及要素间关系（先后/并列/依赖），暂不涉及"怎么做"。
- **重构阶段产出**：基于理解阶段的结构，重新组织出的一条可执行路径——这部分在形态上可以复用现有 `PlanStage[]`（阶段列表）的概念，但阶段的生成不再是"AI 随口列 3-5 步"，而是基于上一步的结构化理解重组而来。
- **呈现阶段状态**：复用现有 `locked`/`confirmed`/`subSteps`/`isExpanded` 这套执行状态机，不需要重新设计。
- **导出产物**：需要新增一个"导出快照"的概念——基于当前 Plan 状态（不管在哪个阶段/进度）生成一份文档或图表内容。

具体字段设计留到下一轮实现时定案，这里只给方向：`Plan` 需要能区分"理解阶段的结构"和"重构/呈现阶段的执行计划"这两层数据，而不是像现在这样只有一层 `stages`。

### 新增模块规划（本轮不创建实际文件，仅占位说明职责）

- **持久化层**：扩展 `electron/store.ts` 或新增一个独立的 plan store（如 `electron/store/plan-store.ts`），把 `Plan` 数据落盘，支持"关闭应用后下次打开能恢复当前计划"，为后续做历史记录留接口。
- **导出/呈现模块**：新增一个模块负责把当前 `Plan` 状态渲染成文档（如 Markdown/PDF）或图表内容，职责上是"读 Plan 状态 → 生成呈现产物"，具体放在 `electron/`（如果需要用 Node 端能力生成文件）还是 `src/lib/`（如果只是渲染成可另存的 HTML/图片）留到实现时根据技术选型定。

## 技术选型（仍然有效，保留）

- **桌面框架**：Electron + electron-vite
- **前端**：React 19 + TypeScript + Tailwind CSS 4 + Framer Motion
- **AI 接入**：多模型切换（OpenAI / Claude / DeepSeek），用户自配 API Key
- **数据存储**：electron-store（现状：仅 settings；下一轮：扩展到 Plan 持久化）
- **打包**：electron-builder → exe 安装包

## 下一轮实施路线图

### 第一步：修复现有链路 + 补持久化
这两项是新方向的地基，不管框架怎么变都用得上：
- 修复"已确认阶段上下文"传递链路（`AIProvider` 接口加参数、prompt 模板里用起来）
- `PlanStage` 类型补上 `confirmed`/`locked` 字段
- 新增 Plan 持久化，支持关闭应用后恢复

### 第二步：理解/重构阶段
- 设计"理解阶段"的 prompt 和数据结构（产出这件事的结构，而不是直接给步骤）
- 设计"重构阶段"如何基于理解阶段的结构生成可执行路径（复用现有 `PlanStage[]` 概念）
- 用 5 个左右差异较大的任务样例手动验证框架普适性，再决定要不要调整

### 第三步：呈现阶段的导出能力
- 设计导出产物的形态（文档 / 图表，或两者都支持）
- 新增导出模块和对应 IPC/UI 入口
- 现有"锁定式渐进展开"执行机制不需要重写，只需要接入新的数据模型

### 第四步（远期，视情况）
- 全局呼出（快捷键/托盘）
- 打包发布
